# Current Status

**Last updated:** November 16, 2026

!!! note "Research implementation"
    Entrabot is a research implementation, not a hosted production service. Run it against an isolated development tenant, and review every permission it requests before granting consent.

## Available today

### Identity and authentication

- Two authenticated session types: certificate-backed Agent User and MSAL delegated.
- Autonomous four-resource provisioning chain: Agent Identity Blueprint → BlueprintPrincipal → Agent Identity → Agent User.
- Blueprint, BlueprintPrincipal, and Agent Identity are created through the dedicated Microsoft Graph v1.0 subtype endpoints; Agent User creation uses Graph beta.
- Certificate private keys are stored in the OS keystore (Keychain, Linux Secret Service, or the Windows certificate store). On Windows both the Blueprint key and setup's Provisioner key are non-exportable CNG keys, created in the TPM when the TPM accepts a key and in the software key store otherwise; no key material is on disk. On macOS and Linux each certificate and its private key are one Keychain or keyring item, named by the certificate's SHA-1 thumbprint, which `.env` records (`ENTRABOT_BLUEPRINT_CERT_SHA1`), so two agents on one account never share or overwrite a key; a key store that cannot be read stops setup and the sign-in, with no fallback to a file. A computer set up before the wizard keeps working with its older single key, which the next setup run stores as the agent's own item.
- Several machines can share a Blueprint: attaching one adds its certificate and keeps the others. `setup.sh --remove-all-existing-certs` is the only way to replace them all. Windows setup registers its certificate the same way, and re-running it registers a certificate an earlier version left unregistered.
- Calling other APIs as the agent: the agent's sign-in gets a token for any API that accepts Entra access tokens, with only the third hop's scope changed. An administrator allows it for one agent with `grant_consent.py --resource-app-id` and takes it back with `revoke_consent.py --resource-app-id`, which since 0.3.1 changes only the grant on that one resource (Microsoft Graph by default). Run for real on Windows 11 against a stand-in API; not run on macOS or Linux. See [Calling Other APIs as the Agent](../guides/other-apis.md).
- Certificate rotation (`scripts\deploy-windows.ps1` on Windows, `./scripts/setup.sh --rotate-cert` on macOS and Linux) keeps the current certificate in use until the new one has signed the agent in, then removes the old one from the Blueprint and deletes it locally with its key.
- Setup on every platform takes over an existing app registration with the Provisioner's name only when that grants nobody anything: an administrator has already approved it for every permission setup needs, or nobody else can use it. Otherwise it stops before changing anything in Microsoft Entra and says how to go on, including naming a checked app for one run with `ENTRABOT_PROVISIONER_APP_ID_VERIFIED`. See [Setup and authentication](../troubleshooting/setup-and-authentication.md#setup-will-not-take-over-an-existing-provisioner-app-registration).
- Setup uses only the Blueprint recorded for the machine, or named when joining, and stops if it is not found or cannot be checked. An existing Agent User found by its sign-in name is reused only when its Agent Identity belongs to that Blueprint; one of another Blueprint stops setup before anything is created, granted or recorded. The Agent Identity and Agent User lookups tell "there is none" from "could not check", and stop on "could not check" instead of creating a duplicate. A Blueprint is named only by its App ID (a GUID). Joining another agent does not carry over an Agent User name that `.env` holds for the previous Blueprint, including after a switch that was interrupted, and setup says so; it stops before the certificate step if the agent step comes back with a Blueprint other than the one asked for. When the wizard stops at the agent step, or because the app `ENTRABOT_PROVISIONER_APP_ID_VERIFIED` names was refused or Microsoft Entra could not be read, it says which.
- Teardown disconnects one computer by default on every platform (`./scripts/teardown.sh`, `scripts\teardown-windows.ps1`): this computer's certificate comes off the Blueprint and is deleted locally with its key, the `entrabot` MCP entries and the settings files go, and the agent and every other computer are kept unless `--delete-agent` (`-DeleteAgent`) is given. The older tenant-wide teardown on macOS and Linux (`./scripts/teardown.sh --tenant-wide`) deletes only the Provisioner app recorded for this machine, by its application ID. With none recorded it deletes no app and prints the command to delete one by hand. It reads `.env` as data and never runs it, keeps the Provisioner token off every command line, shows why a delete failed, and its `--dry-run` resolves targeted Agent User chains read-only.
- The status report (`show_agent_status.py`, run by `status.sh` and `status-windows.ps1`) shows certificate thumbprints by their last four characters; `--full-thumbprints` (`-FullThumbprints`) shows them in full.
- On Windows, an older setup key that setup could not switch off in Microsoft Entra is shown on screen at the provisioning step and on the finish screen, and setup finishes with something to check (exit `3`). The health checks (`-Diagnose` and `status-windows.ps1`) report it as a warning that does not change their exit codes. Teardown takes this PC's certificate and a rotation leftover off the Blueprint in one write, and tries to remove such an older setup key before it deletes the state file. The wizard finds a sponsor whose sign-in name contains an apostrophe.

### Microsoft 365

- Microsoft Teams messaging with explicit chat IDs, plus background chat discovery and polling.
- Outlook read and send, background polling, and daily summaries. The summary goes to every sponsor the directory lists on the Agent Identity whose user record gives an address, and falls back to `.env`'s first `ENTRABOT_HUMAN_USER_MAILS` address only when the directory gives none; the result's `recipient_source` says which (`directory` or `env`). Run for real on macOS against a real agent, without sending: the directory gave the sponsor's address.
- Direct Microsoft Graph Files access alongside Agent 365 Work IQ integrations for Word, Excel, and OneDrive/SharePoint (ODSP).
- Agent 365 telemetry, the first half of Agent 365 integration, opt-in at setup (`--configure-a365`, `-ConfigureA365`, their older names `--configure-a365-observability` and `-ConfigureA365Observability`, or the setup question): content-suppressed `invoke_agent` and `execute_tool` spans through Microsoft's OpenTelemetry Distro (`microsoft-opentelemetry`), from the MCP server and from the harness (PR #122). Setup grants the delegated `Agent365.Observability.OtelWrite` permission, checks as the agent that its token carries it, and only then switches the export on; `--diagnose` reports both. Run for real on macOS against a licensed tenant: setup's step granted the permission, `--diagnose` reported it, and Agent 365 accepted the server's spans (HTTP 200, each span `sent` to every sink, none rejected, content suppressed); see the [Verification Record](verification.md). Microsoft drops the spans unless someone in the tenant has a Microsoft 365 E7 or Agent 365 licence assigned. In the 0.3.0 registry runs on Linux, both portals showed them: Defender's advanced hunting (`CloudAppEvents`) had the agent's tool-call rows from its first telemetry, and in the admin center the registered agent's Activity tab showed its sessions, in both cases including telemetry sent before the agent was registered (see the registry item below). Before it starts the distro, Entrabot sets `MICROSOFT_OTEL_SDKSTATS_DISABLED`, `APPLICATIONINSIGHTS_STATSBEAT_DISABLED_ALL` and `APPLICATIONINSIGHTS_CONTROLPLANE_DISABLED` to `true` (unless already set), which stops the distro's own usage statistics to Application Insights and its settings lookup at `settings.sdk.monitor.azure.com`; Entrabot never enables the distro's Azure Monitor export. Run for real on macOS: with telemetry on, no Azure Monitor or Application Insights host was contacted.
- Registration in the Agent 365 registry (Agent Registry API, Graph beta), the second half of Agent 365 integration: new in 0.3.0. When the person answers yes, setup adds the Microsoft Graph application permission `AgentRegistration.ReadWrite.All` to the setup (Provisioner) app with admin consent, through the signed-in administrator's Azure CLI (never on a no), then runs `scripts/register_agent_instance.py --apply` after the telemetry step; the registration's ID is kept in `.entrabot-state.json`, so a later run updates it. A computer that joined an agent that already existed does not register it again, since the registry cannot be searched. `--diagnose` reports it on its own line, and teardown with `--delete-agent` deletes it. **Run for real on Linux** (Ubuntu 24.04, 2026-11-15, a throwaway agent): setup with `--configure-a365` registered the agent, `--diagnose` reported it registered and Microsoft Graph returned the registration. Before that the agent was not listed in the Microsoft 365 admin center (Agents > All agents > Registry); about a minute after, it was, with platform "Entrabot", the sponsor as owner and the Entra agent ID, and its Activity tab showed sessions from Agent 365 telemetry, including telemetry sent before it was registered. Graph accepted the application IDs setup sends, and the registration ID it returned was the agent identity's ID. That first run found that admin consent can answer success without granting the permission just added; setup now checks the grant and consents again, up to six times. Run for real on Linux with that fix: the grant showed after the third consent, about 50 seconds in, and the agent was registered on the first try in the same run. `register_agent_instance.py --delete --apply` deleted the registration, cleared the recorded ID, and `--diagnose` then said "not registered". Teardown with `--delete-agent` deleted the agent and its registration and exited 0; the admin center still listed the agent about a minute later and no longer did a few minutes later ("Deleted agents" stayed empty). **Run for real on Windows** (Windows 11 Pro 25H2 with a TPM, 2026-11-15, a throwaway agent, setup in the console session of an automatic logon as the computer's built-in Administrator, elevated): the first run took over the tenant's setup app on its earlier approval, created the agent with a TPM-held key and switched telemetry on, but did not register it, because a takeover run gave the setup app nothing. A takeover run now grants this one permission on its own with an app role assignment, and runs no admin consent. Run for real on Windows, on a computer new to the tenant's setup app: the first run granted the permission on its own about 10 seconds in, ran no admin consent, created the agent and registered it, and exited `0`. The second run's admin consent was recorded on the second attempt, about 20 seconds in, and the agent was registered in the same run (exit 0); `-Diagnose` said "registered" and Graph returned it; the admin center listed it; Agent 365 accepted telemetry sent as the agent; `teardown-windows.ps1 -DeleteAgent -Yes` deleted the agent and its registration (exit 0). Not run: macOS, a second computer joining a registered agent, Windows as a standard user. The script still works on its own, dry run by default.
- The Copilot SDK harness (`entrabot`, `src/entrabot/harness/`, PR #122 by Jacob Lyons and Rick Rybinski): an alternative front end that owns its model loop, with a Teams bridge, per-caller permissions and a scheduler. Merged onto `main`'s structure; its own tests pass.
- Bounded, read-only Excel worksheet and range reads through the Graph Workbook API (`list_workbook_worksheets`, `read_workbook_range`). Run against a live tenant on an `.xlsx` in the Agent User's own OneDrive; not yet exercised on a file shared by someone else or on `.xlsm`.

### Security and runtime

- Audit before acting: every tool that sends, creates, shares or deletes writes its audit event first, flushed to disk, and does nothing when that write fails (run for real on macOS: a read-only audit directory stopped a Teams send before Graph). Teams and mail reads and `update_placeholder` are not audited. The audit log is a local JSONL file, not signed. Events the model writes through `audit_log` carry `origin: model`.
- Outbound recipient policy in the server: `send_email` (to, cc, bcc), `create_chat`, `add_teams_member`, `share_file` and the daily summary reach only the agent's directory sponsors, members of the chat the last pushed message came from, and the home tenant, unless `ENTRABOT_OUTBOUND_ALLOW` lists an address or domain. Run for real on macOS: an email and a file share to a reserved domain were refused with no Graph request.
- `--diagnose` has an "Agent sponsor" check: it warns when `.env` names a sponsor who is not among the Agent Identity's sponsors in the directory, when the agent can't read a sponsor's user record, or when the sponsors can't be listed. Run for real on macOS: pass for an agent whose `.env` names its directory sponsor; the warnings are unit-tested.
- Tokens are re-acquired every ten minutes by default (`ENTRABOT_TOKEN_MAX_AGE_SECONDS`; run for real at 60 seconds), which bounds how long a disabled agent keeps acting; continuous access evaluation is not requested because Microsoft does not document it for Agent Users.
- An authoritative external-content boundary wraps untrusted Teams, email, Files, and Work IQ content before it reaches the model.
- Host-gated sponsor reply behavior adapts to the calling client.
- A body-first prompt governs core behavior, with an optional persona layered on top.

### Storage and platforms

- Local operational storage by default, with Azure Blob Storage available as an opt-in.
- With Blob Storage, all shared operational state, including the watched-chat list and email cursor, lives in the container. Instances on one container share it, and exactly one instance pushes a given email.
- Setup and teardown flows for macOS, Linux, and Windows: one setup wizard on all three.
- macOS and Linux setup is one step: `./scripts/setup.sh` needs only Python 3.12 or later, builds `.venv`, and starts the same wizard as Windows, interactive or unattended (`--yes` plus flags). It signs in itself (the browser, or a sign-in code over SSH and on Linux without a display) and offers a private Azure CLI under `~/.entrabot/tools/azure-cli` when there is none. Since 0.3.1 the scripts in `scripts/` find that copy too, and the ones that read with the setup app's token need no Azure CLI (run for real on Ubuntu 24.04; not on Windows or macOS). No `az login`, Git, `sudo` or Homebrew packages besides Python are needed. Every flag it took before still works. `--diagnose` checks a setup without changing it, `--rotate-cert` rotates the certificate, `./start-entrabot.sh` starts the agent, and `./scripts/teardown.sh` disconnects the computer. On Ubuntu 24.04 the wizard (a new agent, a repair, the health check) and the MCP server have been run end to end against a real tenant; on macOS only a repair run and the health check have (see the verification record).
- Windows setup is one step: `scripts\setup-windows.cmd` runs on the Windows PowerShell 5.1 that ships with Windows, needs no administrator rights, PowerShell 7, `winget` or pre-installed Python, and starts an interactive wizard that can also run unattended (`-Yes` plus parameters). `-Diagnose` checks an existing setup without changing it. `start-entrabot.cmd` starts the agent, and both it and setup's last screen say what Claude Code asks the first time; the last screen also lists things to try, matched to the agent's licences.
- Agent licences: setup gives the agent a licence that includes Teams (read from each product's service plans, preferring one with mail and files) and, for Word, Excel and OneDrive files, Microsoft 365 Copilot. When none is free, an interactive run walks the person through it: what the organization has, a free licence given on a yes, or who can add or free one and where in the Microsoft 365 admin center, then checking again. Unattended runs read what the organization has and say what to do on the last screen. Reading and assigning use the setup (Provisioner) credential, through `create_entra_agent_ids.py --licence-report` and `--assign-licence`.
- Word, Excel and OneDrive files (Work IQ), the same on every platform (Word run against a real tenant on Windows and Linux): setup explains them before asking and, after the end-to-end test, switches them on itself, with no Agent 365 CLI, .NET or PowerShell 7 and no sign-in window, so it works over SSH and unattended (`-ConfigureA365WorkIq`, or `--configure-a365-work-iq` on macOS and Linux). It lists the three Work IQ servers in `ToolingManifest.json` from the package's catalog (keeping entries it does not own), gives the agent's Blueprint the permission grants and least-privilege inheritable permissions they need through `ensure_a365_work_iq_permissions.py` (each entry confirmed by reading it back), then checks, as the agent, that its tokens carry the scopes, for about two minutes. A failure there never stops setup and puts the manifest back. When Microsoft has not started honouring the permissions by then, setup finishes with something to check (exit `3`); `-Diagnose` runs the same token check.
- Windows runtime: storage files are UTF-8 and byte-identical across platforms, only one Entrabot server runs per PC, `.env` tolerates a byte-order mark, the persona-sati token command may be a `.ps1`, `.py` or `.cmd` file with arguments (found by absolute path or on `PATH`, never in the current folder), and the Claude Code hooks run through one cross-platform launcher, read their input as UTF-8, and have gates that block when a hook cannot run (on Claude Code 2.1.295 or later, which setup checks for).
- **What the Windows work was verified on.** One configuration: Windows 11 Enterprise 25H2 (x64) in an Azure virtual machine with a virtual TPM 2.0, non-administrator local accounts, driven over SSH. Exercised there: fresh-PC bootstrap; new-agent setup; joining an existing Blueprint; re-run and repair; the interactive wizard in a real terminal; `-Diagnose`; TPM key creation, signing and deletion; the three-hop sign-in; starting the MCP server and calling `whoami`; the single-entry `.env` permission, read back; directory sponsors, including lookup of a personal Microsoft account by its `#EXT#` sign-in name; the Claude Code hooks under Git Bash; the Git for Windows and Claude Code installs and the `PATH` entry for Claude Code; status; certificate rotation; teardown in its default mode and with `-DeleteAgent`; and the full test suite on Windows (4208 passed, 226 skipped, 0 failed). Later, against a real tenant over SSH: the Word, Excel and OneDrive question; the install of the .NET SDK 10 and the Agent 365 CLI with no administrator rights (through `prereqs-windows.ps1 -WithWorkIq`, which setup no longer needs); the read-only licence report and the walkthrough's screens with every Teams licence in use; and the last screen's reminders. By hand from the same machine, without the wizard: the content of `ToolingManifest.json`, the inheritable-permission writes on the Blueprint, and the scopes in the agent's resulting tokens. Then the wizard doing it, over SSH: a brand-new agent with Word, Excel and OneDrive files switched on at the first attempt, an unattended repair run, and `-Diagnose` reporting that the agent's tokens carry every scope they need. An earlier version of Windows setup was acceptance-tested on Windows 11 ARM64; the current setup has not been run there.

## Active development

- Process containment: the MCP server is not contained in 0.3.1; it runs with all of its user's rights. Planned for 0.4.0: process containment of the MCP server on macOS and Linux with Microsoft eXecution Container (MXC), where it is installed, and the system's own sandbox otherwise (Seatbelt on macOS, bubblewrap on Linux), as in [pull request #156](https://github.com/microsoft/entrabot/pull/156). MXC has not been run for real. Windows is not part of it: MXC has open issues there with Python asyncio and stdio servers when egress is denied.
- Planned for 0.5.0: GitHub Copilot SDK harness support, the harness made ready for real use (run against a real Copilot runtime, with the body's audit events and the outbound recipient policy applied to its Teams tools, and Teams state that survives a restart), together with running Entrabot in a container for headless operation. The harness has not been run against a real Copilot runtime, and today its Teams tools lack the audit events and the recipient policy, and its Teams bridge keeps its state in memory (see Known limitations). The design note is in [pull request #161](https://github.com/microsoft/entrabot/pull/161).
- Agent 365 integration's registry half (0.3.0): runs on macOS, with a second computer joining a registered agent, and on Windows as a standard user. The permission grant, the request body and the admin center listing were run for real on Linux and Windows.

## Known limitations

- Entrabot is a research implementation, not a production-ready tenant service.
- Agents with their own user account, which Entrabot creates, are available only to tenants in Microsoft's Frontier preview program (Microsoft Learn, Agent 365 identity, November 2026).
- The recipient policy changes `share_file` and `add_teams_member`: a sponsor's request no longer reaches an address outside the tenant unless it is a sponsor, a member of the requesting chat, or allowlisted.
- The harness's own Teams tools do not write the body's audit events or pass the recipient policy, and its Teams bridge keeps what it has seen in memory, so a message that arrives while it is stopped is not delivered. Its additional-agent path (`entrabot init` with a second name, `scripts/add_agent.py`) was ported onto `main`'s provisioning behind a flag and is unit-tested only.
- The MCP server is not contained: it runs with all of its user's rights and can read and write anything that user can. The recipient policy and audit limit whom it reaches and record what it sends, not what it does on the computer.
- Agent User provisioning still depends on Microsoft Graph beta.
- One agent on two computers with local memory: each computer keeps its own poll cursors, so both push, and both assistants answer, every new Teams message and email; a computer that was off pushes what arrived since its own cursor when it starts. Use cloud memory, or one computer at a time.
- Graph answers 423 Locked for a few minutes when deleting a Word document that Work IQ has just created or read.
- Live smoke tests provision real Entra, Azure, and Microsoft 365 resources and send a real Teams message, so they run manually rather than in CI until an isolated tenant and non-human CI identity are available.
- Windows: not yet tested with the current setup: Windows on ARM64; Windows 10; physical TPM chips (only a virtual TPM was used); PCs joined to Entra or managed by Intune, and tenants with Conditional Access; and cloud memory set up through the Windows wizard. Broader acceptance coverage is tracked in [#105](https://github.com/microsoft/entrabot/issues/105).
- The Windows fixes made after a security review (the Claude Code version check, UTF-8 hook input and gates that block on any error, the persona-sati token command lookup, revoking an older setup key file on the Provisioner app, teardown leaving a certificate that is not in this PC's store, rotation waiting for the new certificate to be listed, and the pinned checksum for the private Python download) are covered by unit tests but have NOT been re-run on a real Windows machine. The end-to-end verification described above predates them.
- The Provisioner take-over rule, the on-screen warning about an older setup key, teardown's one-write Blueprint removal and its retry of an older setup key, and the sponsor search by sign-in name are covered only by unit tests, which the Windows CI job also runs. They have NOT been run against a real tenant. In particular the take-over rule relies on the real output shapes of `az ad app owner list`, `az ad sp show`, and Graph `appRoleAssignments`, which could not be verified offline. If a shape differs, the rule fails closed: setup refuses the take-over and names the override.
- The rule that setup uses only the recorded or named Blueprint and never searches by display name, the check that a reused Agent User belongs to that Blueprint, the "could not check" stops in the Agent Identity and Agent User lookups, `teardown.sh` deleting only the recorded Provisioner app, and the health checks' warning about an older setup key are covered by unit tests. They have not all been run against a real tenant.
- `status.sh` and `scripts/setup_delegated.sh` no longer run `.env` as shell code; tests show a value holding `$(...)`, backticks or `;` runs nothing. Setup still needs an Entra administrator (below).
- The tenant-wide `teardown.sh` changes above (`.env` read as data, the token kept off command lines, the delete messages, the targeted `--dry-run`) and the status report's thumbprint masking were run for real on Ubuntu 24.04 (bash 5.2, GNOME Keyring in a headless session) against a real tenant, with a throwaway agent created by the `setup.sh` from before the wizard (`--new`, from a folder with no `.venv` and an empty keyring): `teardown.sh --dry-run`, alone and with `--agent-user-upn`; a real teardown, then the same teardown again to see an agent that is already gone reported as "already deleted" (the text `az ad user delete` prints for a missing user is the one teardown looks for); a `.env` carrying `$(...)`, backticks and bare commands, which ran nothing; and the status report with and without `--full-thumbprints`. Plain `teardown.sh` was the tenant-wide teardown then; it now has to be asked for (`--tenant-wide`). Not run for real: any of it on macOS (unit tests, on bash 3.2); the wait for a newly registered Provisioner certificate, which did not happen to be needed on the run that had the fix; and the wizard's handling of an interrupted switch.
- Those Linux runs found three faults in the bash setup and teardown that the wizard now stands in for, none of which has been run for real on macOS or Linux in its new form: plain `teardown.sh` deleted the Provisioner app every agent in the tenant shares (the default teardown now disconnects one computer and leaves the app alone; `--tenant-wide` still deletes it unless `--preserve-provisioner` is given); nothing ever removed a computer's setup certificate from that app, so one was left behind per computer (the default teardown removes this computer's once no other agent here needs it; the ones already left behind are not cleaned up); and `setup.sh` ended with "Setup complete!" and blamed a licence "just assigned" when the agent had no Teams licence at all (the wizard's last screen says which licence is missing and what to do).
- Setting up an agent needs an Entra administrator on every platform. Granting admin consent needs a Global Administrator or Privileged Role Administrator, and joining an existing agent from another machine still needs directory rights, because each machine adds its own credential to the Provisioner app and the Blueprint. A person without those rights cannot set up an agent by themselves; there is no "administrator prepares, user joins" flow yet.
- An agent needs a licence that includes Teams to use Teams. Setup completes without one, says so, and exits with a "something to check" code. At a terminal it first offers the licence walkthrough.
- Windows: the wizard's "set up, but not honoured yet" ending for Word, Excel and OneDrive files, and a failed permissions step putting `ToolingManifest.json` back, have unit tests only. Setup stopped using Microsoft's Agent 365 CLI because its sign-in failed over SSH (`MsalAuthenticationFailedException`) and, at the desktop, it added Windows sign-in prompts of its own. In the last run through the CLI, at the desktop, granting the Work IQ permissions failed on a new agent with a 404 from Microsoft Graph (a second permission added to a grant created moments before). That step now writes each resource's permissions once and tries again on a 404; run against the half-made grant the failure left, it completed it, and a second run changed nothing. On a new Windows 11 PC (2026-11-14), the wizard's first run then failed at the Blueprint's inheritable permissions although it had written them: a read after Word's entry had been read back did not show it, and writing it again was refused with `400` "already exists", so setup said Word, Excel and OneDrive files could not be switched on. A second run a few minutes later changed nothing and switched them on. An "already exists" answer now counts as written once a read shows the entry, and any other refusal still fails. Run for real on Windows 11 from the 0.3.0 release branch (2026-11-15) with Graph's read made to lag once: Graph answered the create with `400` "already exists", the script read the entry back and reported it written (exit `0`, entry unchanged), and 0.2.0's script failed on the same answer. Not run on Linux or macOS.
- **On macOS only a repair run and the health check have been run against a real tenant,** on a copy of a setup made before the wizard: the older single Keychain key was kept and stored as the agent's own item, nothing new was registered, and the agent signed in. Not run on macOS: a new agent, the questions at a terminal, rotation, teardown. On Ubuntu 24.04.5 (a server with no desktop, GNOME Keyring in `dbus-run-session`) the wizard was run against a real tenant with throwaway agents: a new agent, unattended and at a terminal, with and without Word, Excel and OneDrive files; `--diagnose` and `./status.sh`; certificate rotation; joining from a second folder; `--remove-all-existing-certs` and the repair of the folder it cut off; a folder set up by the `setup.sh` from before the wizard being taken over with its key kept; setup's private Azure CLI; and teardown (one folder disconnected, `--delete-agent --purge-data`, and the tenant-wide teardown targeted at one agent). Not run on either system: cloud memory set up to the end (the test account may not assign roles in its subscription, so only the failure was seen), giving the agent a licence (the tenant had no free one), a first run that waits for a new setup certificate (Microsoft accepted it at once each time), and starting the agent from the last screen (no Claude Code on the test computer). The rest on macOS is covered by unit and script tests only: `scripts/setup.sh`, `scripts/teardown.sh` and `start-entrabot.sh` were run for real under the bash 3.2 that ships with macOS, against a stub interpreter, and the Keychain store was round-tripped for real on macOS (create, find, test-sign, read back, delete).
- On macOS and Linux the agent's key is read into the process to sign: it is not hardware-backed and not non-exportable. The key store must be unlocked in the session that runs setup and the agent: a Mac's login keychain is usually locked over SSH (`security unlock-keychain`), and a Linux server with no desktop needs a Secret Service keyring started and unlocked in a D-Bus session. Setup does not install Claude Code on macOS or Linux.
- Windows: covered by unit tests only, not yet run against a real tenant: giving the agent a licence through the walkthrough, the Microsoft 365 Copilot path, setup removing a sign-in the directory refuses before it asks for a new one (the browser sign-in itself was run at the desktop and worked), `winget` drawing its progress bar in place in `prereqs-windows.ps1`, and the changes made after the last run on the test machine (the last screen pointing back to the walkthrough, Copilot only when Word, Excel and OneDrive files are on, readable names for products Microsoft's reference does not list, a failed Word, Excel and OneDrive step never stopping setup, and the review screen naming an Azure CLI installed before it).
- When Word, Excel and OneDrive files are switched on, the Microsoft 365 Copilot licence is assigned at the step that creates the agent, before they are configured; if their configuration then fails, the licence stays assigned for the next run.
- On Windows, Claude Code needs Git for Windows to run this repository's hooks. Without it the hook gates block edits and Teams sends.
- In a Windows remote session (SSH), Windows Credential Manager and MSI-based installers are unavailable. Setup does not depend on either; this is why it uses private copies of Python and the Azure CLI when they are missing.
- Local storage files are read and written as UTF-8 ([#60](https://github.com/microsoft/entrabot/issues/60)) and the single-instance lock now also holds on Windows, with its file descriptor closed on every error path ([#59](https://github.com/microsoft/entrabot/issues/59)). Both issues are still open pending review of these changes.
- Legacy Graph file comments are not the same as Word UI comments; use the Work IQ Word tools for document comments.
- Work IQ Excel (`mcp_ExcelServer`) is in the live Agent 365 catalog but not on Microsoft Learn, and the CLI warns of a "legacy ATG audience", so its tools may change. It requires `McpServers.Excel.All` on the Blueprint.
- `ENTRABOT_FILES_DENIED_SITES` is checked against Graph's reported site only for the workbook and Work IQ Excel tools. The Work IQ Word and ODSP tools don't apply it, and `read_file` and `add_file_comment` check the `site_id` the caller supplies.
- Excel writes, table reads, and workbook sessions aren't implemented ([#117](https://github.com/microsoft/entrabot/issues/117)).
- External-content wrapping is defense in depth. It reduces instruction-injection risk but is not proof against every possible model jailbreak.
- On a cloud backend, the email cursor starts at "now" when its key is first created (the first boot on a container, or after the key is deleted), so mail received before then isn't pushed; it stays readable through `read_email`. Once the key exists, a restart reuses it and mail received during downtime is pushed as normal. See [Upgrading to shared poll state](../troubleshooting/migrations-and-upgrades.md#upgrading-to-shared-poll-state).
- An instance on a host that ignores channel notifications can still claim Teams and email deliveries, so with mixed hosts on one container an item can go to the host that can't show it.
- Two emails with the same timestamp, where the second arrives after the cursor has moved past it, won't be pushed. Both stay readable through `read_email`.
- The shutdown save stops waiting after 10 seconds, but a storage call already in flight can still delay process exit until the storage client's own timeout.
- A batch of email held because its claim couldn't be confirmed lives only in memory, so restarting before the claim settles loses it. The mail stays readable through `read_email`.
- Chats are polled one at a time and each read sees the latest 10 messages, so a very busy chat can have messages pushed past that window between visits. They stay readable through `read_teams_messages`.
- Delegated sessions have no discovery sweep, so with a cloud backend their chat list only grows through `create_chat`.
- A wait keeps the sponsor gate it started with, so a gate built during a brief storage or Graph failure can miss a federated sponsor until the next wait.
- Failed watched-list writes retry on the next discovery sweep and at shutdown, so in a delegated session a failed write can wait until shutdown. Discovery re-adds the chat in an Agent User session.
- If the sponsor lookup fails, a sponsor's Teams push arrives in the XPIA envelope like anyone else's until a later lookup succeeds, so the agent may ask them to restate an instruction. Someone removed as a sponsor can keep speaking outside the envelope for up to 15 minutes, until the cached list refreshes.
- Adding a Blueprint certificate reads the list and then writes it, and those two steps aren't atomic. Two machines attaching in the same moment can lose one of the new certificates; the affected machine's setup reports it, and re-running setup there adds it again. A per-user lock keeps two setups on the same machine from overlapping, but it can't cover two machines.
- `ENTRABOT_MODE` is validated but does not currently select the auth path in `_init_auth`; credential presence and `ENTRABOT_SKIP_PROVISIONING` determine which path (three-hop Agent User or MSAL delegated) is attempted.
